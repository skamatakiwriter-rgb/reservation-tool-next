# 予約管理ツール Ver2 配車・回収管理基本設計書

作成日：2026年9月23日  
更新日：2026年10月3日

## 1. 文書の目的

本書は、公開済みの予約管理ツールVer1を残し、その予約情報を配車・回収作業へ引き継ぐVer2の基本設計を定める。

Ver2は、産業廃棄物収集運搬事業者を想定したポートフォリオ用公開デモである。実在する勤務先、顧客、車両、担当者、回収先、運用規則、実データは使用しない。

本書では、次を実装前の基準として整理する。

- Ver1から残す機能とVer2で追加する機能
- 予約と配車の責任分界
- 配車担当者とドライバーの業務フロー
- 回収量の不確実性と回収結果の扱い
- 画面、データ、保存、履歴、例外処理
- 初期版の対象外と受入条件

コード変更、ブランチ作成、データ移行、公開設定は本書の作成範囲に含めない。

## 2. Ver2の位置付け

### 2.1 Ver1

Ver1は、次の業務を扱う完成済み公開デモとして残す。

```text
申込み
→ 受付
→ 内容・日程確認
→ 確定
→ 完了または取消
```

Ver1の`v1.0.0`タグは変更しない。Ver2の開発によって、Ver1の完成記録、設計資料、公開デモを未完成扱いにしない。

### 2.2 Ver2

Ver2は、Ver1の確定予約を社内の配車・回収作業へ引き継ぐ拡張版とする。

```text
申込み
→ 受付
→ 内容・日程確認
→ 確定
→ 未配車
→ 車両・ドライバー割当
→ 回収開始記録（任意）
→ 回収結果記録
→ 完了または再配車
```

Ver2の主目的は、依頼時に入力された情報を配車担当者とドライバーが再入力せずに利用できるようにすることである。

### 2.3 ポートフォリオ上の説明

Ver1とVer2は、別々の無関係な作品ではなく、同じ業務ツールの段階的な発展として扱う。

- Ver1：依頼者と受付担当者をつなぐ予約管理
- Ver2：予約確定後の配車・回収までつなぐ業務拡張

Ver2では、回収量が事前申告と異なり得ることを前提に、完全自動配車ではなく、人の判断を支援する設計を示す。

## 3. 解決する課題

- 受付済みの依頼内容を配車表へ再入力する手間を減らす。
- 未配車、配車済み、回収中、回収結果を一つの流れで確認できるようにする。
- 配車担当者が画面を往復せず、依頼内容を見ながら配車登録できるようにする。
- 顧客の申告内容、社内での補足、ドライバーへの指示を混同しない。
- 回収量の申告と現地実績が異なっても、履歴を失わずに回収結果を記録できるようにする。
- 一部回収や回収不可の場合に、元の予約を誤って完了させず再配車へつなぐ。
- 配車後の重要な予約変更を見落としにくくする。

## 4. 利用者と役割

| 役割 | Ver2で行うこと |
|---|---|
| 依頼者 | Ver1の利用者画面から回収依頼を申し込む |
| 受付担当者 | 依頼内容と日程を確認し、予約を確定・変更・取消する |
| 配車担当者 | 確定予約を確認し、車両、ドライバー、予定時刻、指示を登録する。電話報告を受けた場合は作業結果を代理登録する。搬入判断待ち、電話相談後の積み置き、保留解除を記録する |
| 管理者 | ドライバーマスターを登録・編集し、新規配車へ使用しない担当者を無効化する |
| ドライバー | 自分の担当案件を確認し、必要に応じて回収開始を記録し、回収結果を記録する。搬入不能は電話で配車担当者へ報告し、車両保留の状況は閲覧のみ行う |
| デモ利用者 | パスワードなしの役割別入口から架空データを操作する |

公開デモでは本番認証と権限管理を実装しない。役割別画面は操作の違いを示すためのデモであり、未認証の本番利用を許容する設計ではない。

## 5. 対象カテゴリー

| カテゴリー | 配車対象 | 扱い |
|---|---:|---|
| 蛍光管持込 | いいえ | 依頼者が持ち込むため、Ver1の予約管理だけで完結する |
| 家具家財撤去 | はい | 車両と主担当ドライバーを割り当てる |
| ビン缶回収 | はい | 収集車両と主担当ドライバーを割り当てる |

カテゴリー定義へ`requiresDispatch`を追加する。初期値は次とする。

```text
keikoukan = false
kagu       = true
binkan     = true
```

初期版では、複数車両、複数ドライバー、補助作業員の詳細割当を扱わない。家具家財撤去で追加人員が必要な場合は、社内補足またはドライバー向け指示へ記録する。

## 6. 予約と配車の責任分界

### 6.1 予約が管理するもの

- 依頼者と連絡先
- 回収先
- 希望日と確定した予約日
- カテゴリー
- 依頼時の申告内容
- 予約の受付、確定、完了、取消
- 予約内容の変更履歴
- 同じ作業をまとめる`workGroupId`

### 6.2 配車が管理するもの

- 配車対象となる予約
- 予定日、開始予定時刻、終了予定時刻
- 収集車両
- 主担当ドライバー
- 社内補足
- ドライバー向け指示
- 配車済み、回収中、作業終了、配車取消
- 回収結果
- 配車後の予約変更確認
- 再配車の履歴

### 6.3 分離の原則

- 予約状態へ未配車、配車済み、回収中を追加しない。
- 配車状態を変更しても、定めた連動条件以外では予約状態を自動変更しない。
- 顧客が入力した依頼内容を配車担当者が上書きしない。
- 配車担当者の補足とドライバーへの指示は、依頼内容とは別項目で保存する。

## 7. 状態

### 7.1 予約状態

Ver1の状態を変更しない。

| 値 | 表示 | 意味 |
|---|---|---|
| `received` | 受付 | 申込みを受け、内容または日程の調整前 |
| `confirmed` | 確定 | 内容と日程が確定 |
| `completed` | 完了 | 持込、撤去または回収が完了 |
| `cancelled` | 取消 | 予約を論理取消 |

### 7.2 配車状態

| 値 | 表示 | 意味 |
|---|---|---|
| `assigned` | 配車済み | 車両、ドライバー、予定時刻が決定 |
| `inProgress` | 回収中 | ドライバーまたは配車担当者が任意の回収開始を記録 |
| `completed` | 作業終了 | 今回の配車単位を終了し、回収結果を記録済み |
| `cancelled` | 配車取消 | 今回の配車を取り消した |

「未配車」は保存状態にしない。次の条件を満たす予約を画面上で未配車と判定する。

```text
予約がconfirmed
かつカテゴリーが配車対象
かつassignedまたはinProgressの配車記録がない
かつ直近の終了結果が一部回収または回収不可ではない
```

有効な配車がなく、直近の終了結果が一部回収なら「要再配車」、回収不可なら「要対応」と判定する。新しい配車を登録した後は、要再配車または要対応の表示から外し、配車済みとして表示する。

### 7.3 回収結果

配車状態を`completed`へ変更するとき、次のいずれかを必須で選ぶ。回収開始記録は任意であり、`assigned`から直接`completed`へ変更してよい。現地から電話報告があっても、同じ日・同じ車両・同じ主担当ドライバーで回収を続ける場合は結果を登録せず、`assigned`または`inProgress`の現在状態を維持する。

| 値 | 表示 | 予約への影響 |
|---|---|---|
| `allCollected` | 全量回収 | 予約を`completed`にする |
| `partiallyCollected` | 一部回収 | 予約は`confirmed`のまま残し、要再配車として表示する |
| `notCollected` | 回収できず | 予約は`confirmed`のまま残し、まず要対応として表示する |

一部回収または回収不可では、今回の配車記録を終了済み履歴として残し、新しい配車を登録できるようにする。

`partiallyCollected`は、車両へ一度積み込んだ時点の途中経過を表す状態ではない。今回の配車単位を終了する時点で未回収分が残り、別日または別の車両・ドライバーによる対応が必要な場合に使用する。

回収できない品目の混在、申告を超える量、回収前に判明した搬入先の受入停止など、理由は作業結果メモへ自由記述する。今回まったく回収していなければ「回収できず」、一部を回収して現地に残りがあれば「一部回収」を選ぶ。回収後に搬入できなくなった場合は回収結果と搬入状況を混同せず、次節の車両保留として扱う。

### 7.4 回収後の搬入判断・積み置き

搬入先へ向かう道や受入状況により、現地回収後に搬入できない場合がある。ドライバーは配車担当者へ電話で報告し、配車担当者が電話相談の結果が出るまでを「搬入判断待ち」、車両に積んだまま待機する判断後を「積み置き中」として車両に記録する。解除も配車担当者が行う。解除予定日時は必須にしない。相談記録、理由、対象予約・配車、車両、開始・解除日時と操作者を履歴に残す。

これは現地回収の結果とは別の社内運用状態である。全量回収の報告を受けた予約は従来どおり完了とし、搬入判断待ち・積み置き中でも完了を取り消さない。ただし保留中の車両は、期限を推測せず新規配車と別案件の回収開始・作業結果登録に使用できない。すでに登録済みの将来の配車は自動取消せず、管理画面で警告し、別車両への変更または保留解除を担当者に促す。搬入できた、または別の方法で積載が解消されたと確認したら、理由を記録して保留を解除する。搬入完了を通常案件ごとに記録する機能や法定帳票の代替は初期版に含めない。

## 8. 回収量とメモの扱い

### 8.1 依頼時の回収量

依頼者が入力する数量は、正確性を保証できない参考情報として扱う。現地では申告より少ない、または大幅に多い場合があるため、初期版では次を行わない。

- 申告量から車両を自動決定する。
- 申告量だけで配車登録を禁止する。
- 申告量と車両積載量を厳密に自動照合する。
- 申告量を回収実績として上書きする。

画面には「依頼時申告・目安」であることを表示する。

### 8.2 情報の区分

| 区分 | 編集者 | 用途 |
|---|---|---|
| 依頼内容 | 依頼者。保存後は管理画面で原文を確認 | 顧客が申告した品目、数量、状況 |
| 社内補足 | 受付担当者・配車担当者 | 電話確認、現場条件、量の不確実性等 |
| ドライバー向け指示 | 配車担当者 | 現場担当者へ伝える注意事項 |
| 回収結果 | ドライバーまたは管理者 | 実際の量、全量・一部・回収不可、結果メモ |

予約内容を変更する正式操作と、社内補足の追記を区別する。社内補足の編集によって顧客の申告内容を変更しない。

### 8.3 社内補足

社内補足は、顧客の申込み後に受付担当者または配車担当者が電話確認・社内確認で得た、顧客入力欄に含まれない補助情報を社内で共有するための記録とする。

記載例：

```text
9月23日に電話確認。
倉庫の奥にも回収物があり、申告の5袋から最大10袋程度へ増える可能性あり。
現場前の道路が狭いため、大型車は進入しにくいとのこと。
到着前に担当者へ連絡が必要。
```

対象となる情報：

- 申告量より増減する可能性
- 電話確認で判明した追加品目
- 依頼者自身も把握できていない未確定情報
- 道路幅、車高、駐車場所、階段等の現場条件
- 立会いや到着前連絡の必要性
- 受付時点で確認できなかった事項
- 日程変更や車両選定の判断経緯
- 前回の一部回収の残り等、再配車時の背景

社内補足は単一の文字列を上書きする方式にせず、予約に紐づく追記履歴として保存する。

```text
9/23 10:15　受付担当
電話確認。申告より量が増える可能性あり。

9/23 13:40　配車担当
道路幅を考慮して2t車を候補とする。

9/24 09:10　受付担当
依頼者へ再確認。到着前連絡を希望。
```

記載ルール：

- 1件ごとに記録日時と操作者を自動保存する。
- 保存済みの補足を上書き・削除しない。
- 誤記を訂正するときは、訂正内容を新しい補足として追記する。
- 顧客には表示しない。
- ドライバーへ自動表示せず、現場で必要な内容だけを配車担当者がドライバー向け指示へ整理する。
- 日付、車両、ドライバー、配車状態、回収結果等の構造化項目を社内補足だけで代用しない。
- 業務上不要な個人情報、主観的・感情的な評価、差別的または攻撃的な記載を残さない。

### 8.4 回収結果メモ

作業終了時に、次を保存する。

- 回収結果区分
- 実際の回収内容・量を表す自由記述
- 一部回収または回収不可の理由
- 次回対応に必要な補足
- 終了日時と操作者

初期版では実績数量を必ず数値化せず、単位の異なる品目をまとめて自由記述できるようにする。

出発前の電話確認等で申告数量が変わった場合は予約の依頼内容を更新し、配車済みなら要再確認にする。現地で判明した申告との差は予約の申告内容を実績に書き換えず、今回の作業終了時に「実際の回収内容・量」として記録する。同日継続中は途中報告のたびに入力しない。

## 9. 業務フロー

### 9.1 受付から未配車まで

1. 依頼者がVer1の利用者画面から申し込む。
2. 家具家財撤去・ビン缶回収は`received`で保存する。
3. 受付担当者が内容と日程を確認する。
4. 必要に応じて予約内容を変更し、社内補足を記録する。
5. 予約を`confirmed`へ変更する。
6. 配車対象で有効な配車記録がなければ、予約一覧の配車状況へ「未配車」と表示する。

受付状態の配車欄にも「配車を登録する」を無効状態で表示し、「予約を確定すると配車を登録できます」と操作順を案内する。予約確定後に操作可能とし、配車済みでは「配車を変更する」へ表示を切り替える。

### 9.2 配車登録

1. 配車担当者が予約一覧で「未配車」の予約を選ぶ。
2. 開いた予約詳細内で依頼内容と社内補足を確認する。
3. 必要に応じて社内補足とドライバー向け指示を入力する。
4. 予定日、開始時刻、終了時刻、車両、ドライバーを選ぶ。
5. 車両・ドライバーの時間重複と予約の最新状態を保存直前に確認する。
6. 問題がなければ`assigned`の配車記録を保存する。
7. 予約一覧の配車状況を「未配車」から「配車済み」へ更新する。

### 9.3 回収作業

1. ドライバーが担当案件を確認する。
2. 開始時刻を残したい場合だけ「回収開始を記録」を実行し、配車状態を`inProgress`にする。開始記録は必須ではない。
3. 開始記録を省略する場合は`assigned`のまま作業を行い、作業結果を直接登録できる。
4. 現地から電話報告があっても、同じ日・同じ車両・同じ主担当ドライバーでそのまま回収を続ける場合は画面操作を行わず、`assigned`または`inProgress`の現在状態を維持する。
5. 今回の配車単位を終える時点で、全量回収、一部回収、回収できずのいずれかを選ぶ。
6. 実際の回収内容と、結果に応じて必要な結果メモを入力する。
7. 「作業結果を保存して終了」で`assigned`または`inProgress`から`completed`にする。
8. 全量回収なら予約も`completed`にする。
9. 回収済み分が残ったまま別日へ持ち越す場合、または同日でも車両・主担当ドライバーを替えて対応する場合は、一部回収として今回の配車を終了する。作業未着手の変更は現在の配車を変更する。
10. 一部回収または回収不可なら予約を`confirmed`のまま残し、要再配車または要対応として再表示する。

電話報告の内容を社内で残す必要がある場合に限り、受付担当者または配車担当者が社内補足を任意で追記する。通常の同日継続について、途中報告や積込回数の登録を必須にしない。

### 9.4 再配車

1. 一部回収の予約を「要再配車」、回収不可の予約を「要対応」として予約一覧の配車状況へ表示する。
2. 前回の配車と回収結果を確認できるようにする。
3. 回収不可では、配車担当者が理由を確認して再配車するか、配車以外の対応を行うか判断する。
4. 再配車する場合は、新しい予定日、車両、ドライバー、予定時刻を登録する。
5. 同じ予約に対する配車回数を履歴で確認できるようにする。

有効な配車は1予約につき1件までとする。終了済みまたは取消済みの配車記録は複数保持できる。

通常の車両・主担当ドライバーの変更は出発前に行う運用とし、`assigned`の現在の配車を変更して配車回数を増やさない。変更のたびに未着手確認のチェック操作は求めない。すでに一部を回収し、同日中でも車両または主担当ドライバーを替える例外的な場合は、今回の配車を一部回収で終了してから新しい配車を登録する。同じ日・同じ車両・同じ主担当ドライバーで回収を続けるだけの場合は再配車しない。

回収開始記録を省略した`assigned`は、画面上だけでは出発・作業開始を判定できない。Ver2初期版では通常の配車変更・取消は出発前に行う前提とし、状態と最新版の検証を行う。取消には従来の確認ダイアログで「作業前の取消」であることを示す。出発後の車両故障等は例外運用として配車担当者が電話等で調整し、現地で一部回収済みなら通常の変更・取消をせず、一部回収の結果を登録する。`inProgress`は通常の配車変更・取消を拒否する。開始記録を省略した出発後変更をデータだけで防止することはできず、本番運用では別途管理が必要である。

## 10. 配車ルール

### 10.1 配車可能条件

次をすべて満たす場合だけ配車登録できる。

- 予約が存在する。
- 予約状態が`confirmed`である。
- カテゴリーが配車対象である。
- 同じ予約に`assigned`または`inProgress`の配車がない。
- 初回配車では、予定日が予約の`requestedDate`と一致する。
- 開始予定時刻が終了予定時刻より前である。
- 車両とドライバーが有効である。
- 同じ時間帯に同じ車両またはドライバーの有効な配車がない。

初回配車の予定日は予約の`requestedDate`と一致させる。一部回収または回収不可後の再配車では、依頼者との調整結果に基づき別の予定日を登録できる。再配車予定日を登録しても、元の予約日と過去の配車履歴を上書きしない。

### 10.2 時間重複

同じ車両またはドライバーに、時間帯が重なる配車を登録できない。予定が隣接し、前の終了時刻と次の開始時刻が同じ場合は重複としない。

初期版では移動時間の自動計算を行わない。配車担当者が移動時間を含めて予定時刻を入力する。

搬入判断待ち・積み置き中の車両は、時間帯の重複がなくても新しい配車で選択できない。保留開始前から登録済みの配車は履歴を維持し、保留中はその車両で回収開始・作業結果登録できない。

### 10.3 配車後の予約変更

`assigned`または`inProgress`の配車がある予約について、次の情報が変更された場合は要再確認にする。

- 予約日
- 回収先住所
- カテゴリー別依頼内容（申告数量を含む）
- 顧客の連絡事項

配車記録へ、割当時の予約版と、最後に変更確認した予約版を保存する。重要項目を変更した場合に`needsReview`を有効にし、未確認差分は「最後に変更確認した時点」と現在を比較する。割当時の情報は履歴として保持し、通常の差分確認には使わない。重要項目以外の変更で予約版だけが進んでも要再確認にしない。

配車担当者は変更内容が現在の配車に影響しないか確認し、必要なら車両、ドライバー、時刻、指示を変更してから「変更内容を確認済みにする」を実行する。この操作は、配車を再確定する操作や、変更後の予約内容を画面へ反映する操作ではなく、配車担当者が変更の影響を確認した記録である。確認前から管理画面・ドライバー画面には最新の予約内容を表示する。

未確認の重要変更がある予約は、管理カレンダーの予約日へ「配車要確認 N件」、選択日の予約へ「要再確認」、予約一覧の配車状況へ「要再確認」を表示する。変更差分は管理画面とドライバー画面で同じ基準を使用する。ドライバー画面では、上部警告に加え、予約日、回収先、依頼時申告、顧客連絡事項のうち変更された欄へ「要確認」「変更前」「現在」を表示する。ドライバーには確認済み操作や配車担当者への連絡を求めず、要再確認中でも回収開始・作業結果登録を行える。管理画面で確認済みにすると、管理上の要再確認表示とドライバー画面の変更警告を消す。

`inProgress`中の重要変更は警告を表示し、自動的に配車を取り消さない。

予約日を変更して`assigned`の予定日と異なる場合は、配車予定日も合わせて変更し、重複を再確認してから確認済みにする。カテゴリーごとに申込入口が分かれているため、Ver2では配車の有無にかかわらず既存予約のカテゴリーを変更しない。変更が必要な場合は元予約を取り消し、正しいカテゴリーで新しい予約を再受付する。元予約と新予約は別の予約ID・受付番号とし、既存の再受付履歴で相互にたどれるようにする。`assigned`の配車があれば予約取消と同時に配車も取り消す。`inProgress`では通常の予約取消を拒否するため、この手順は使わず例外対応とする。数量などの申告内容は同じ予約のまま変更でき、有効配車があれば要再確認にする。完成済みのVer1公開デモは変更しない。

### 10.4 予約取消

`assigned`の配車がある予約を取り消す場合、同じ保存処理で配車も`cancelled`にし、車両とドライバーの予定から外す。

`inProgress`の配車がある予約は、通常の取消操作を拒否する。回収中止として配車結果を記録するか、管理者向けの例外手順を別途検討する。初期版では回収中の予約取消を実装しない。

配車対象の予約は、管理画面の従来の「予約を完了」操作で直接完了させない。全量回収の作業結果を保存したときだけ予約と配車を一括で完了する。配車対象外の蛍光管持込は従来の完了操作を維持する。Ver1から移行した配車記録のない完了予約は、その履歴を変更しない。

## 11. 画面構成

### 11.1 既存画面

| URL | Ver2での扱い |
|---|---|
| `/` | Ver1の入口を残し、予約・配車管理とドライバーデモへの案内を追加する |
| `/reserve` | 依頼者向け予約画面を維持する |
| `/admin` | 予約一覧と既存の予約詳細を維持し、配車状況、配車入力、作業結果、履歴を統合する |
| `/driver` | 架空ドライバーの担当予定と作業結果を扱う |
| `/guide` | 公開デモ全体の確認順序と画面別の使い方を案内する |
| `/demo-data` | 全画面共通のデモデータ管理として、初期状態への復元と削除を扱う |

### 11.2 予約一覧・予約詳細への配車統合

Ver2初期版では、専用の配車管理画面や日別配車盤を新設しない。既存の`/admin`で予約と配車を続けて扱い、対象予約を別画面で選び直す手間をなくす。

管理カレンダーの「すべて」表示では、日付ごとの総予約件数に加え、受付停止または上限超過があるカテゴリー数を文字付きラベルで表示する。色だけで状態を伝えず、一部カテゴリーの停止を全カテゴリー停止と誤認させない。カテゴリー選択時は、そのカテゴリーの予約数／上限数と「受付停止」「上限超過」を表示する。日付を選択すると、詳細領域でカテゴリーごとの予約数／上限数と「受付可」「満枠」「受付停止」「上限超過」を確認できるようにする。

予約一覧では、予約状態と配車状況を別の列または別の文字付きバッジで表示する。予約の取消・受付・完了を先に判定し、終了済み配車の結果だけを理由に取消済み予約へ「要再配車」を表示しない。

配車状況の表示候補：

- 配車対象外
- 未配車
- 配車済み
- 回収中
- 要再配車
- 要対応
- 要再確認
- 全量回収済み
- 配車取消履歴あり（予約詳細で確認）

配車だけを取り消した確定予約は「未配車」とし、取消履歴があることを詳細で示す。Ver1から移行した配車記録のない完了予約は「Ver1完了・配車記録なし」と表示する。

搬入判断待ち・積み置き中は予約状態や配車状況を置き換えず、対象予約の詳細と車両選択欄に別の警告として表示する。管理画面では保留中の車両と影響する将来の配車を確認できるようにする。

予約一覧では日付、予約状態、配車状況、カテゴリー、受付番号、会社名等で絞り込めるようにする。行を選択すると既存の予約詳細を開き、次の領域を上から順に表示する。

1. 予約情報
2. 顧客の依頼内容
3. 社内補足と追記
4. 配車（予定日・予定時刻・車両・主担当ドライバー・指示・保存／変更）
5. 作業結果
6. 配車・回収履歴

重複検出時は保存を停止し、重複する予定の日時と対象予約を示す。可能な場合は、その予約詳細を開く導線を表示する。

スマートフォンでは、予約一覧から予約詳細を開き、同じ詳細内の各領域を縦に表示する。配車入力中の値は、詳細内の領域を移動しても保持する。

### 11.3 ドライバー画面

URL案：`/driver`

公開デモでは、架空のドライバーを選択し、そのドライバーの担当案件だけを表示する。初期表示は本日とし、今日、明日、今後7日、最大31日の任意期間へ切り替えられる。複数日の結果は日付別・時刻順にまとめる。

表示項目：

- 指定期間の担当案件
- 回収予定時刻
- 会社名
- 回収先
- 依頼時申告
- ドライバー向け指示
- 配車後の変更警告
- 任意の回収開始記録
- 回収結果入力
- 作業終了操作

同日継続のためのボタンや入力欄は設けない。回収中のまま作業を続け、今回の配車単位を終える時だけ結果を登録する。

ドライバー画面では、顧客の依頼内容や配車担当者の指示を編集できない。

### 11.4 予約詳細の追加表示・操作

既存の予約詳細へ次を追加する。

- 配車要否
- 未配車、配車済み、回収中、回収結果
- 車両、ドライバー、予定時刻
- 要再確認表示
- 過去の配車・回収結果
- 社内補足の表示と追記
- 配車の登録・変更・取消
- 配車担当者による作業結果の代理登録

## 12. データ設計

### 12.1 Reservation

Ver1の予約構造と識別子を維持する。社内補足は予約本体の`contactNotes`や単一の`internalNotes`へ追加せず、12.5節の独立した追記記録として保存する。

予約ID、受付番号、`workGroupId`、関連番号の意味を変更しない。

| `isActive` | 必須 | 配車選択に使用できるか |
| `version` | 必須 | 競合検出用 |
| `loadHold` | 任意 | 搬入判断待ち・積み置き中の記録。対象予約・配車、理由、相談内容、開始日時・操作者を保持 |

| `isActive` | 必須 | 配車選択に使用できるか |

### 12.4 DispatchAssignment

1件のデータを、同じ予定日・車両・主担当ドライバーで行う1回の配車単位として扱う。同じ条件のまま同日中に複数回積み込み・運搬しても、配車記録を分割しない。

| 項目 | 必須 | 説明 |
|---|---:|---|
| `dispatchId` | 必須 | 配車記録の内部ID |
| `reservationId` | 必須 | 対象予約ID |
| `attemptNumber` | 必須 | 同じ予約に対する配車単位の回数 |
| `plannedDate` | 必須 | 配車予定日 |
| `plannedStartTime` | 必須 | 開始予定時刻 |
| `plannedEndTime` | 必須 | 終了予定時刻 |
| `vehicleId` | 必須 | 割当車両 |
| `primaryDriverId` | 必須 | 主担当ドライバー |
| `status` | 必須 | `assigned`、`inProgress`、`completed`、`cancelled` |
| `reservationVersionAtAssignment` | 必須 | 割当時の予約版 |
| `reservationSnapshotAtAssignment` | 必須 | 割当時の重要な予約項目。履歴として上書きしない |
| `reservationVersionAtLastReview` | 必須 | 最後に変更確認した予約版 |
| `reservationSnapshotAtLastReview` | 必須 | 最後に確認した重要な予約項目。差分表示の基準 |

| `driverInstructions` | 任意 | ドライバー向け指示 |

| `completedAt` / `completedBy` | 条件付き | 作業終了記録 |
| `outcome` | 条件付き | 全量、一部、回収不可 |
| `actualCollectionSummary` | 条件付き | 実際の回収内容・量 |
| `outcomeNotes` | 条件付き | 一部回収、回収不可、次回対応等 |
| `cancelledAt` / `cancelledBy` | 条件付き | 配車取消記録 |
| `createdAt` / `createdBy` | 必須 | 作成記録 |
| `updatedAt` / `updatedBy` | 必須 | 最終更新記録 |
| `version` | 必須 | 競合検出用 |

### 12.5 InternalNote

1件のデータを1回の社内補足追記として扱う。

| 項目 | 必須 | 説明 |
|---|---:|---|
| `noteId` | 必須 | 社内補足の内部ID |
| `reservationId` | 必須 | 対象予約ID |
| `body` | 必須 | 1～500文字の補足本文 |
| `createdAt` | 必須 | 追記日時 |
| `createdBy` | 必須 | 追記した受付担当者または配車担当者 |

社内補足は追記専用とし、初期版では更新・削除操作を設けない。誤記の訂正は、新しい社内補足を追記して行う。

### 12.6 AuditLog

既存の履歴構造を拡張し、`entityType`へ`dispatch`、`vehicle`、`driver`、`internalNote`を追加する。

最低限、次を記録する。

- 配車登録・変更・取消
- 回収開始
- 作業終了と回収結果
- 再配車
- 配車後変更の検出と確認
- 社内補足の追記
- 車両・ドライバーの有効状態変更を将来実装した場合の操作

## 13. 保存と整合性

### 13.1 IndexedDB

Ver2初期版もVer1と同じブラウザ内保存を使用する。データベースのバージョンを上げ、次のストアを追加する。

- `vehicles`
- `drivers`
- `dispatchAssignments`
- `internalNotes`

必要な索引：

- 配車記録の`reservationId`
- 配車記録の`plannedDate`
- 配車記録の`vehicleId`と予定時間
- 配車記録の`primaryDriverId`と予定時間
- 社内補足の`reservationId`と`createdAt`

### 13.2 Ver1データの移行

- 既存の予約、設定、受付停止、履歴を削除しない。
- 新ストアとVer2用初期データだけを追加する。
- 既存データに配車記録がない場合、確定済みの配車対象予約は未配車として表示する。
- 移行に失敗した場合に自動初期化しない。

### 13.3 更新単位

次は同じトランザクションで保存する。

- 配車登録、配車履歴、冪等記録
- 配車変更、変更履歴、冪等記録
- 回収開始、開始履歴、冪等記録
- 全量回収時の配車完了、予約完了、双方の履歴、冪等記録
- 全量回収と同時に搬入判断待ちを申告した場合の配車完了、予約完了、車両保留、履歴、冪等記録
- 搬入判断待ちから積み置き中への変更、または保留解除時の車両、履歴、冪等記録
- 一部回収・回収不可時の配車完了、結果履歴、冪等記録
- 予約取消時の配車取消、予約取消、双方の履歴、冪等記録
- 社内補足の追記、操作履歴、冪等記録

保存途中で片方だけ更新された状態を作らない。

### 13.4 競合と再送

- 配車登録・変更・開始・終了・取消にも冪等キーを使用する。
- 表示時の予約版、配車版と保存時の最新版が異なる場合は上書きしない。
- 同じ処理IDと同じ内容の再送では、同じ結果を返す。
- 保存結果が不明な場合は、処理済み記録を照会してから再実行する。

## 14. 初期データ

Ver2の初期データには、すべて架空の次の例を含める。

- 配車対象外の蛍光管持込
- 確定済み・未配車の回収案件
- 車両とドライバーが割当済みの案件
- 回収中の案件
- 全量回収済みの案件
- 一部回収により要再配車となった案件
- 回収不可で要対応となった案件
- 全量回収済みの案件に紐づく、搬入判断待ちまたは積み置き中の架空車両
- 配車後に予約内容が変更され、要再確認となった案件
- 時間重複を確認できる車両・ドライバーの予定
- 電話確認、量の不確実性、現場条件を時系列で確認できる社内補足

車両・ドライバーは少数の架空初期データを用意し、管理画面から追加、編集、有効・無効切替を行えるようにする。削除は行わず、過去の配車記録から参照できる状態を維持する。

## 15. ダッシュボード

管理画面に、少なくとも次を表示する。

- 本日の回収予定
- 未配車
- 配車済み
- 回収中
- 全量回収済み
- 要再配車
- 要対応
- 配車後変更・要再確認
- 予定日を過ぎた未完了予約

予定日を過ぎた未完了予約は、確定予約について、有効配車があればその配車予定日、なければ予約日を日本時間の今日と比較して判定する。完了・取消予約は数えない。

確定済み・配車対象・未配車の予約は、予約日を基準に次の配車期限警告を表示する。日数は日本時間のカレンダー日で数える。

- 予約日が2日後：事前警告。「2日後の未配車」として、できれば本日中の配車を促す。
- 予約日が翌日：至急警告。「明日の未配車」として、遅くとも前日中の配車確定を促す。
- 予約日が当日：至急警告。「本日の未配車」として、直ちに対応を促す。

受付、配車対象外、配車済み、回収中、完了、取消は配車期限警告へ含めない。一部回収後と回収不可は単純な配車忘れと混同せず、従来どおり「要再配車」「要対応」として表示する。警告からは対象日・未配車の予約一覧へ移動できるようにする。

次を優先的な注意項目として表示する。

- 本日予定なのに未配車
- 配車後に重要情報が変更された
- 一部回収または回収不可で次の対応が未登録
- 予定日を過ぎても予約が完了していない

初期版では高度なグラフや分析を実装しない。

## 16. エラー表示と復帰

| 状況 | 画面の対応 |
|---|---|
| 最新状態で予約が取消済み | 配車保存を停止し、最新内容を再読込する |
| 別画面で配車済み | 二重配車を保存せず、既存配車を表示する |
| 車両・ドライバーの時間重複 | 保存を停止し、重複する予定を表示する |
| 予約または配車の版競合 | 入力を失わず、最新情報と再確認方法を示す |
| IndexedDB保存失敗 | 成功表示へ進まず、再試行または入力保持を案内する |
| 回収結果の必須情報不足 | 結果と必要メモを入力するまで終了を保存しない |
| 他タブで初期化・削除 | 古い参照を破棄し、最新のデモ状態へ戻す |

エラー発生時に予約や配車を自動削除しない。

## 17. Ver2初期版の対象外

- 本番認証、実在する利用者アカウント、詳細な権限管理
- 複数端末間のリアルタイム共有
- GAS、Googleスプレッドシート、外部データベースとの接続
- Googleマップ、経路検索、ルート最適化
- GPS追跡と現在地表示
- LINE、メール、Web Push通知
- 申告量による車両の自動選択
- 積載量、廃棄物種類、混載等の自動適合判定
- 複数車両、複数ドライバー、作業員シフトの詳細管理
- 写真、署名、添付ファイル
- マニフェスト管理や法令対応機能
- 料金計算、請求、売上管理連携
- OCR、AI入力補助、自動配車
- 車両・ドライバーの削除、一括取込、本番用組織・権限管理

これらは、実利用者の業務確認またはVer2初期版の完成後に必要性を判断する。

## 18. デモと本番の境界

Ver2公開デモでは次を明記する。

- データは同じブラウザ・同じ公開元のIndexedDBに保存する。
- 異なる端末、ブラウザ、利用者とは共有しない。
- 予約・配車管理とドライバーの入口に本番認証はない。
- 実在する会社名、氏名、住所、電話番号、車両番号を入力しない。
- 申告量と車両の適合を保証しない。
- 業務フローと例外処理を確認するためのデモであり、本番運用可能性や業務削減効果を証明するものではない。

本番化する場合は、認証、権限、共有データベース、バックアップ、端末、通知、個人情報、実際の配車規則を別途設計する。

## 19. 開発段階

### Phase 1：Ver2基盤

- Ver1完成地点からVer2開発ブランチを作成
- Ver1回帰テストの基準を固定
- カテゴリーの配車要否追加
- IndexedDBスキーマ移行
- 車両、ドライバー、配車記録、履歴を追加
- 社内補足の追記記録を追加
- Ver2初期データを追加

### Phase 2：配車登録

- 予約一覧への配車状況列・絞り込み追加
- 既存の予約詳細への依頼内容、社内補足、前回結果、配車入力の統合
- 車両、ドライバー、予定時刻、指示の登録
- 車両・ドライバー重複確認
- 予約詳細への配車情報・操作追加

### Phase 3：回収作業

- ドライバー画面
- 任意の回収開始記録と、開始記録なしの作業結果登録
- 同日・同一車両・同一担当者での継続時は追加入力なし
- 全量、一部、回収不可の結果入力
- 全量回収時の予約完了連動
- 回収後の搬入判断待ち・積み置き中の車両保留と解除
- 一部・回収不可時の再配車

### Phase 4：変更・例外

- 配車後の予約変更検出
- 要再確認と確認済み操作
- 予約取消と配車取消の連動
- 競合、再送、保存失敗からの復帰
- ダッシュボード注意表示

### Phase 5：検査と公開準備

- Ver1の既存テストとVer2追加テスト
- 型検査、Lint、本番ビルド
- 架空データと表示文言の確認
- Ver2操作ガイド、README、ポートフォリオ紹介
- Ver1とは別のVer2公開URL
- `v2.0.0`タグによる完成版固定

## 21. 実装前に残る確認事項

搬入判断待ち・積み置きは7.4節と20.5節で初期版に含める方針を確定した。公開後の反応で入力項目や運用を見直す。残る確認事項は、後から決定できるVer2公開用Netlifyサイトの名称である。

社内補足は、予約本体の単一文字列ではなく、予約に紐づく独立した追記履歴として採用済みである。

架空車両・架空ドライバー、Ver2開発ブランチ、DB版、初期データ版は18番実装指示書で採用値を定めた。専用配車画面は初期版へ設けず、予約一覧と予約詳細へ統合する方針を採用済みである。

車両マスターは初期版へ追加し、車両ナンバーを主識別表示とする。別の表示名は新規登録せず、車両コードを自動採番する。未完了配車または車両保留がある車両の無効化は拒否し、車両削除、車検・整備・保険等の車両台帳機能は対象外とする。

回収中止の管理者向け例外操作はVer2初期版へ含めず、回収中予約の通常取消を拒否する方針で確定した。
