本書は、Ver2の配車・回収管理で追加するデータ、IndexedDBスキーマ、状態判定、保存単位、競合・再送、Ver1からの移行を実装可能な詳細へ落とし込む。

## 2. 設計原則

- Ver1の予約ID、受付番号、作業グループID、状態、保存先を維持する。
- 配車状態を予約状態へ追加せず、予約と配車を別データとして保存する。
- 顧客の依頼内容、社内補足、ドライバー向け指示、作業結果を別項目・別責任で保存する。
- 同日・同じ車両・同じ主担当ドライバーで回収を続ける場合は、追加データを保存しない。
- 一部回収は途中経過ではなく、今回の配車単位を終了して未回収分が残った結果として保存する。
- 保存途中で予約だけ、配車だけ、履歴だけが更新された状態を作らない。
- 表示用の「未配車」「要再配車」「要対応」は正本として重複保存せず、予約と配車から判定する。
- 公開デモでは架空データだけを使用し、ブラウザ内保存の制約を維持する。

## 4. 共通形式

### 4.1 識別子

- 内部IDはUUID等の衝突しにくい文字列とする。
- 表示用コードと内部IDを分ける。
- 内部IDは更新、再配車、初期化前の同一世代内で変更しない。
- 初期化後は新しい`generationId`を発行し、以前と同じ表示コードがあっても別世代として扱う。

### 4.2 日付と時刻

| 用途 | 形式 |
|---|---|
| 業務日・予定日 | 日本時間の`YYYY-MM-DD` |
| 予定時刻 | ゼロ埋めした24時間表記`HH:mm` |
| 作成・更新・開始・終了日時 | ISO 8601日時文字列 |

予定日時は`plannedDate`、`plannedStartTime`、`plannedEndTime`に分ける。公開デモではタイムゾーン設定を別項目として保存せず、日本時間の業務日として扱う。

### 4.3 操作者

Ver1の操作者を維持し、ドライバー操作を追加する。

```text
demo-user
demo-admin
demo-system
demo-driver:<driverId>
```

配車担当者が電話報告を受けて代理登録した場合は`demo-admin`、ドライバー画面から登録した場合は`demo-driver:<driverId>`を保存する。表示名だけを操作者IDとして使用しない。

### 4.4 文字列

- 保存前に前後の空白を除去する。
- 空白だけの必須文字列を拒否する。
- 改行を含む自由記述は最大文字数を適用する。
- 画面表示時にHTMLとして実行しない。

## 6. Reservationの扱い

### 6.1 構造

Ver1の`Reservation`構造を維持し、配車ID、車両ID、ドライバーID、社内補足を予約本体へ埋め込まない。

### 6.2 配車可能な予約

次をすべて満たす予約だけを配車対象とする。

- 予約が存在する。
- `status`が`confirmed`である。
- カテゴリーの`requiresDispatch`が`true`である。
- `assigned`または`inProgress`の有効な配車が存在しない。

初回配車では`plannedDate`を予約の`requestedDate`と一致させる。一部回収または回収不可後の再配車では、調整後の別日を許可し、予約の`requestedDate`は上書きしない。

### 6.3 予約変更と配車再確認

有効な配車がある予約で、次のいずれかが変わった場合は、同じ保存処理で配車の`needsReview`を`true`にする。

- `requestedDate`
- `address`
- `categoryAnswers`（申告数量を含む）
- `contactNotes`

会社名、担当者名、電話番号だけの変更は初期版では自動的な要再確認条件に含めない。ただし画面は常に予約の最新値を表示する。

`assigned`または`inProgress`の配車が要再確認の場合も、警告と差分を表示したまま回収開始記録・作業結果登録を許可する。要再確認は配車担当者による変更影響の確認管理であり、ドライバーの確認済み操作や配車担当者への連絡を作業条件にしない。要再確認は重要項目の変更でのみ設定し、予約版だけが変わったことを理由に設定しない。

`assigned`の予約日変更後、配車予定日が新しい予約日と異なる場合は、予定日を更新して時間重複を検証するまで変更確認済みにできない。Ver2の既存予約では配車の有無にかかわらず`categoryId`変更を画面で無効化し、`updateReservation`でも拒否して予約・配車を変更しない。カテゴリー変更が必要なら元予約を取り消して新カテゴリーで別の予約を再受付する。既存の再受付元IDと相互履歴を使い、同じ予約IDのカテゴリーだけを書き換えない。`assigned`の取消は配車取消と一括保存し、`inProgress`の通常取消は拒否する。Ver1の完成済み公開デモは変更しない。

### 6.4 予約取消との連動

- `assigned`の配車がある予約を取り消す場合、予約取消と配車取消を同じトランザクションで保存する。
- `inProgress`の配車がある予約は通常の予約取消を拒否する。
- 有効な配車がない予約はVer1と同様に取り消せる。
- 終了済み・取消済みの過去配車は削除しない。

配車対象の予約を従来の`changeStatus(completed)`で直接完了させない。予約完了は全量回収の`completeDispatch`から一括保存する。配車対象外の予約は従来の完了操作を許可する。Ver1から移行した配車記録のない完了予約は変更しない。

| `version` | 正整数 | 必須 | 初期値1。更新ごとに増加 |
| `loadHold` | 下記の保留記録 | 任意 | 搬入判断待ち・積み置き中のみ設定。解除時は削除し監査履歴を残す |

### 7.2 規則

- 少数の架空車両を初期データとして用意し、管理画面から追加・編集・有効無効切替を行える。
- 新規登録時は全車両の`vehicleCode`末尾の最大数へ1を加え、`VEH-0001`形式で採番する。削除・番号再利用は行わない。
- `registrationNumber`はNFKC正規化後、空白とハイフンを除いた比較キーで同一世代内の重複を拒否する。表示値は入力された車両ナンバーを前後空白除去して保持する。
- 画面表示は`registrationNumber`を優先し、旧データだけ`displayName`へフォールバックする。
- `isActive=false`でも過去配車からの参照・表示を維持する。
- `capacityNote`は自動車両選択、積載保証、保存拒否に使用しない。
- 車両ナンバー、車種、積載参考情報、用途・注意事項の変更では車両コードを維持し、版と監査履歴を更新する。
- 別車両への入替では既存レコードを使い回さず、既存車両を無効化して新規登録する。
- `assigned`または`inProgress`の配車、または`loadHold`がある車両は無効化できない。

### 7.3 搬入判断待ち・積み置き中の記録

`loadHold`は`status`（`decisionPending`または`storedOnVehicle`）、`reservationId`、`dispatchId`、`reason`（1～500文字）、`consultationNote`（0～500文字）、`startedAt`、`startedBy`を保持する。1車両につき有効な保留は1件までとし、解除予定日時は保存条件にしない。`storedOnVehicle`への変更では電話相談の判断内容を`consultationNote`に記録する。解除時は解除理由、日時、操作者を監査履歴に残し、`loadHold`を消して車両版を増やす。

保留は現地回収の結果と独立する。紐づく配車は、実際に回収した`allCollected`または`partiallyCollected`の終了済み配車に限る。`notCollected`へは紐づけない。過去の予約や配車を削除・未完了へ戻さない。

## 9. DispatchAssignment

### 9.1 配車単位

1件を、同じ予定日・車両・主担当ドライバーで行う1回の配車単位とする。同じ条件のまま同日中に複数回積み込み・運搬しても、別の配車記録を作らない。

回収済み分があり別日へ持ち越す場合、または同日でも車両・主担当ドライバーを変更する場合は、元の配車を一部回収で終了し、新しい配車を作成する。通常の出発前変更は現在の`assigned`配車を変更し、`attemptNumber`を増やさない。

開始記録を省略した`assigned`から出発・現地作業の有無は判定できない。Ver2初期版では通常変更・取消を出発前の操作として扱い、未着手確認を保存APIの入力条件にしない。取消は画面の確認ダイアログで作業前の操作であることを示す。回収済み分があれば通常変更・取消を行わず、一部回収として今回の配車を終了する。`inProgress`では通常変更・取消を拒否する。この区別は担当者の業務判断に依存する。

| `plannedDate` | `YYYY-MM-DD` | 必須 | 初回は予約日、再配車は別日可 |
| `plannedStartTime` | `HH:mm` | 必須 | 終了時刻より前 |
| `plannedEndTime` | `HH:mm` | 必須 | 開始時刻より後 |
| `vehicleId` | 文字列 | 必須 | 存在する有効車両ID |
| `primaryDriverId` | 文字列 | 必須 | 存在する有効ドライバーID |

### 9.3 予約スナップショット

割当時と最終確認時のスナップショットには次だけを保存する。

```text
requestedDate
categoryId
address
categoryAnswers
contactNotes
```

`categoryId`は割当時の記録用にスナップショットへ残すが、Ver2では既存予約のカテゴリー変更を許可しない。画面表示用の未確認差分は、現在の予約と`reservationSnapshotAtLastReview`を比較して作る。履歴用の`reservationSnapshotAtAssignment`は上書きしない。`reservationVersionAtAssignment`と現在の予約版が異なるだけでは`needsReview`にしない。

「変更を確認済みにする」では、現在の予約版と重要項目を最終確認版・スナップショットへ保存し、`needsReview=false`にする。確認操作そのものと配車変更は別操作として履歴を残す。

### 9.4 状態別の整合条件

| 状態 | 必須条件 | 禁止・空にする項目 |
|---|---|---|
| `assigned` | 割当項目、作成・更新記録 | 開始、終了、結果、取消記録なし |
| `inProgress` | `startedAt`、`startedBy` | 終了、結果、取消記録なし |
| `completed` | 終了、`outcome`。開始記録がある場合は`startedAt`と`startedBy`の両方 | 取消記録なし。開始記録は任意 |
| `cancelled` | `cancelledAt`、`cancelledBy` | 開始、終了、結果なし。初期版では`assigned`からだけ遷移 |

保存済みの`completed`または`cancelled`を通常操作で他状態へ戻さない。

### 9.5 作業結果

| 値 | 表示 | 予約への影響 | 入力条件 |
|---|---|---|---|
| `allCollected` | 全量回収 | 予約も`completed`へ変更 | 実際の回収内容・結果メモは任意 |
| `partiallyCollected` | 一部回収 | 予約は`confirmed`。要再配車 | 実際の回収内容・結果メモが必須 |
| `notCollected` | 回収できず | 予約は`confirmed`。要対応 | 結果メモが必須。実際の回収内容は任意 |

`partiallyCollected`は同日継続の途中保存に使用しない。同日・同じ車両・同じ主担当ドライバーで継続する場合、配車データ、監査履歴、冪等記録を追加しない。

出発前に判明した申告数量の変更は予約の`categoryAnswers`へ保存し、有効配車があれば`needsReview`を設定する。現地で判明した回収実績は配車の`actualCollectionSummary`へ作業終了時に保存し、予約の`categoryAnswers`を実績値で上書きしない。

### 9.6 有効配車の一意性

`assigned`または`inProgress`を有効配車とする。同じ予約には有効配車を最大1件だけ許可する。

IndexedDBの単純な一意索引だけでは状態条件付き一意性を表せないため、配車作成トランザクション内で対象予約の全配車を読み、有効配車がないことを確認する。

### 9.7 attemptNumber

新しい配車の`attemptNumber`は、同じトランザクション内で対象予約の既存配車を読み、最大値に1を加えて決定する。取消済み配車も配車回数に含め、番号を再利用しない。

## 14. Ver1からVer2への移行

### 14.1 移行原則

- DB更新時に既存ストアを削除・再作成しない。
- 既存の予約、設定、停止、履歴、冪等記録を消去・再採番しない。
- `onupgradeneeded`では不足する4ストアと索引だけを作成する。
- 移行失敗時に初期データへ自動置換しない。

### 14.2 既存のactiveデータ

Ver1の`DemoMetadata.lifecycleState`が`active`で、7日失効していない場合は次の論理移行を行う。

1. 既存6ストアと新規4ストアを含む1つのreadwriteトランザクションを開始する。
2. 現在のメタデータがスキーマ1であることを確認する。
3. 既存予約、設定、停止、履歴、冪等記録を変更しない。
4. 新規ストアが空なら、固定の架空車両・架空ドライバーだけを追加する。
5. 配車と社内補足は空のままとする。
6. `DemoMetadata.schemaVersion`を2、`seedVersion`をVer2値へ更新する。
7. 履歴へスキーマ移行の事実を個人情報なしで記録する。

この場合、確定済みの家具家財撤去・ビン缶回収は、配車履歴がないため未配車として表示する。

### 14.3 新規開始・初期状態へ戻す場合

Ver2導入後の新規開始、明示的な初期状態への復元、7日失効後の再生成では、Ver2用の完全な初期データを作成する。これには車両、ドライバー、配車、社内補足の確認例を含める。

### 14.4 deleted状態

`lifecycleState=deleted`のメタデータは個人情報を含まない技術情報として保持する。次にデモを開始するときは新しい`generationId`でVer2初期データを作成する。

### 14.5 現行初期化処理の変更点

現行実装はスキーマ版または初期データ版が異なると全ストアを初期データで置き換える。Ver2では、版の不一致を次の2種類に分ける。

- 移行可能な旧スキーマ：既存データを保持して論理移行する。
- 新規、明示的リセット、失効済み、deletedからの再開始：Ver2初期データを生成する。

単なる`SCHEMA_VERSION`または`SEED_VERSION`の不一致を、既存データ全消去の条件にしない。

## 15. 表示状態の判定

予約状態を先に判定してから、配車の表示状態を次の順で判定する。

1. 予約が`cancelled`なら「予約取消」、`received`なら「配車前」とする。
2. 予約が配車対象外なら「配車対象外」とする。
3. 配車対象の予約が`completed`で配車記録がなければ「Ver1完了・配車記録なし」とする。
4. `assigned`または`inProgress`の有効配車を確認する。
5. 有効配車がなければ、終了日時が最新の`completed`配車を確認する。
6. 終了済み配車がなければ、確定予約は未配車とする。

| 条件 | 表示状態 |
|---|---|
| 予約が`cancelled` | 予約取消。終了済み配車の結果から要再配車を表示しない |
| 予約が`received` | 配車前 |
| 配車対象外カテゴリー | 配車対象外 |
| 配車対象の完了予約・配車記録なし | Ver1完了・配車記録なし |
| 有効配車が`assigned` | 配車済み |
| 有効配車が`inProgress` | 回収中 |
| 有効配車の`needsReview=true` | 上記状態に要再確認を併記 |
| 有効配車なし・最新完了結果が一部回収 | 要再配車 |
| 有効配車なし・最新完了結果が回収不可 | 要対応 |
| 有効配車なし・最新完了結果が全量回収 | 全量回収済み |
| 有効配車なし・完了結果なし・予約が確定 | 未配車 |

取消済み配車は最新作業結果の判定から除外する。例えば一部回収後に再配車を登録して取り消した場合、以前の一部回収結果が再び要再配車の根拠となる。一方、終了結果がなく配車だけを取り消した確定予約は未配車とし、配車取消は履歴に表示する。

同じ予約に有効配車が複数ある等の不整合を検出した場合は、任意の1件を正しいものとして隠さず、データエラーとして操作を停止する。

### 15.1 配車期限警告の判定

配車期限警告は保存項目を追加せず、予約・配車と日本時間の今日から都度算出する。`dispatchDisplayState`が`unassigned`の予約だけを対象とし、`requestedDate`が今日、翌日、2日後のいずれかに一致する場合にそれぞれ当日、前日、2日前警告へ分類する。

`needsRedispatch`、`needsAttention`、`assigned`、`inProgress`は対象外とする。この判定により、一部回収や回収不可を新規配車の登録忘れとして誤表示しない。警告の表示・非表示によって予約、配車、履歴を更新しない。

## 16. 時間重複判定

比較対象は、同じ`plannedDate`で`assigned`または`inProgress`の配車とする。

次を満たす場合に時間重複とする。

```text
既存の開始時刻 < 新しい終了時刻
かつ
新しい開始時刻 < 既存の終了時刻
```

終了時刻と次の開始時刻が同じ場合は重複しない。配車変更では自分自身の`dispatchId`を除外する。車両または主担当ドライバーのどちらか一方でも重複すれば保存を拒否し、該当する配車IDを結果へ含める。

初期版では移動時間、休憩時間、積載量、混載可否を自動判定しない。

`Vehicle.loadHold`がある車両は、予定日・時間にかかわらず新規配車で選択できない。既存配車の車両変更では変更先が保留中でないことを確認する。保留開始前に作成済みの配車は自動取消せず警告対象とし、保留中の車両では別案件の回収開始・作業結果登録を拒否する。

## 17. 操作別の保存設計

すべての書込み操作で、最初に`generationId`と冪等記録を確認し、処理済みでなければ最新状態と期待版を検証する。

### 17.1 配車登録

同じトランザクションで読むもの：

- メタデータ、冪等記録
- 対象予約
- 対象予約の既存配車
- 車両、ドライバー
- 同日の車両・ドライバー配車

同じトランザクションで保存するもの：

- 新しい`DispatchAssignment`
- `dispatchCreated`履歴
- 冪等記録
- メタデータの最終利用日時

画面で確認した予約版を入力として受け取り、保存直前に最新版との一致を確認する。予約状態、配車対象、有効配車の有無、初回・再配車の日付条件、時間重複、選択車両の保留なしも再確認する。

### 17.2 配車変更

- `assigned`だけを変更できる。
- 通常の出発前変更として扱い、未着手確認の追加入力は要求しない。回収済み分があれば通常変更ではなく作業結果を登録する。
- 表示時の配車版と最新版を照合する。
- 表示時の予約版と最新版も照合する。
- 車両・ドライバー・日付・時刻の重複を再確認する。
- 変更先車両が保留中なら拒否する。保留中の車両から別車両への変更は許可する。
- `reservationVersionAtAssignment`と割当時スナップショットは変更しない。
- 配車、変更履歴、冪等記録、メタデータを同時保存する。

### 17.3 回収開始

- 回収開始記録は任意とし、記録しなくても作業結果を登録できる。
- `assigned`から`inProgress`だけを許可する。
- `needsReview=true`でも開始を許可する。要再確認は配車担当者の確認管理であり、ドライバーの確認操作や連絡を開始条件にしない。
- 対象車両が搬入判断待ち・積み置き中なら、保留開始前から登録済みの配車でも開始を拒否する。
- 対象配車版と現在の予約状態を確認する。
- `startedAt`と`startedBy`を保存し、配車版を増やす。
- 配車、開始履歴、冪等記録、メタデータを同時保存する。

### 17.4 作業結果登録

- `assigned`または`inProgress`から`completed`への変更を許可する。
- 対象車両に別の終了済み配車に紐づく有効保留があれば、開始記録を省略した場合も含めて登録を拒否する。
- 表示時の予約版・配車版と保存時の最新版を照合し、予約が`confirmed`で配車対象であることを確認する。
- `assigned`から登録する場合は`startedAt`と`startedBy`を生成しない。
- `assigned`または`inProgress`で`needsReview=true`の場合も登録を許可する。要再確認の表示と差分は、作業結果登録まで確認できる状態を維持する。
- 結果別の必須項目を検証する。
- `completedAt`、`completedBy`、結果を保存し、配車版を増やす。
- 同日継続ではこの操作を呼び出さない。
- 実際に回収した案件で、配車担当者（デモ操作者`demo-admin`）が同時に搬入判断待ちを申告した場合は、作業結果と車両保留を同一トランザクションで保存する。ドライバーによる作業結果登録には車両保留の同時入力を許さない。後から搬入不能が判明した場合は17.10節の操作を使う。

全量回収では次を同時保存する。

- 配車の作業終了
- 予約の`completed`への変更、完了日時・操作者、予約版の増加
- 配車完了履歴、予約完了履歴
- 冪等記録、メタデータ

一部回収・回収不可では予約を`confirmed`のまま維持し、配車完了履歴、冪等記録、メタデータを同時保存する。

### 17.5 配車取消

- 初期版では`assigned`から`cancelled`だけを許可する。
- 出発前の取消として扱い、未着手確認の追加入力は要求しない。画面の確認ダイアログで作業前の操作であることを示す。
- `cancelledAt`、`cancelledBy`、任意の理由を保存する。
- 予約状態は変更しない。
- 配車、取消履歴、冪等記録、メタデータを同時保存する。

### 17.6 予約取消と配車取消

`assigned`の配車がある予約を取り消す場合は、出発前の取消として画面で内容を確認し、予約、配車、双方の履歴、冪等記録、メタデータを1トランザクションで更新する。未着手確認の追加入力は要求せず、どちらか一方だけを取り消さない。配車対象予約の直接完了は拒否し、全量回収の作業結果登録から完了させる。

### 17.7 予約変更と要再確認

- 予約変更前後の重要項目を比較する。
- 有効配車があり重要項目が変わった場合、原則として`needsReview=true`にして配車版を増やす。予約版だけの変更では設定しない。
- 配車の有無にかかわらず`categoryId`の変更を先に拒否し、予約変更と配車取消を暗黙に連動させない。カテゴリー変更は明示的な予約取消と新規再受付に分ける。`categoryAnswers`内の申告数量などの変更は、有効配車があれば重要項目として扱う。
- 予約、予約変更履歴、配車、`dispatchReviewRequired`履歴、冪等記録、メタデータを同時保存する。
- 重要項目が変わらない場合は配車を更新しない。

### 17.8 変更確認済み

- 対象配車が`assigned`または`inProgress`であることを確認する。
- 表示時の予約版と配車版の両方を照合する。
- 現在の予約版と重要項目を最終確認版・スナップショットに保存する。
- `needsReview=false`として配車版を増やす。
- `assigned`で予約日と配車予定日が異なる場合は確認済みにできず、配車予定日変更と時間重複の再検査を先に行う。
- 配車、確認履歴、冪等記録、メタデータを同時保存する。

### 17.9 社内補足追加

- 対象予約の存在を確認する。
- 本文を検証する。
- 補足、追加履歴、冪等記録、メタデータを同時保存する。
- 既存補足を更新しない。

### 17.10 車両の搬入判断待ち・積み置き・解除

- `startVehicleLoadHold`は配車担当者の操作とし、実際に回収した終了済み配車とその車両を照合し、期待車両版と有効保留なしを確認する。理由は必須、解除予定日時は不要。車両保留、履歴、冪等記録、メタデータを同時保存する。
- `confirmVehicleLoadHold`は配車担当者の操作とし、`decisionPending`だけを`storedOnVehicle`へ変更する。電話相談の判断内容を必須とし、車両版、履歴、冪等記録を同時保存する。
- `releaseVehicleLoadHold`は配車担当者の操作とし、`decisionPending`または`storedOnVehicle`を対象とする。搬入・積替えなど積載が解消した理由を必須とする。車両の`loadHold`を削除し、解除履歴、冪等記録を同時保存する。搬入できたことを自動推定して解除しない。
- デモの操作者記録は保留操作を`demo-admin`とし、ドライバー画面から保留操作を公開しない。本番の認証・権限管理を実現したと誤解させない。
- 各操作で世代、冪等キー、車両版、対象配車との整合を確認する。既存の将来配車は自動変更せず、保留中は開始を拒否する。解除後は通常の配車規則で車両を使用できる。

### 17.11 車両マスター登録・編集・有効無効切替

- `createVehicle`は車両ナンバーと車種を検証し、車両ナンバーの重複を確認して車両コードを自動採番する。車両、追加履歴、冪等記録、メタデータを同時保存する。
- `updateVehicle`は期待車両版を確認し、車両ナンバー、車種、積載参考情報、用途・注意事項を更新する。車両コードと有効状態、車両保留は変更せず、変更履歴を保存する。
- `setVehicleActive`は期待車両版を確認する。無効化時に未完了配車または車両保留があれば拒否し、有効・無効変更と履歴を保存する。
- 同じ処理IDの再送では初回結果を返し、車両、採番、履歴を重複させない。

## 18. 保存結果

Ver1の保存結果を維持し、配車用に次を追加する。

| 結果 | 意味 |
|---|---|
| `activeDispatchExists` | 同じ予約に有効な配車がある |
| `reservationNotDispatchable` | 予約状態またはカテゴリーが配車条件を満たさない |
| `vehicleUnavailable` | 車両が存在しない、または無効 |
| `vehicleRegistrationConflict` | 同じ車両ナンバーが登録済み |
| `vehicleHasActiveDispatches` | 未完了配車があるため車両を無効化できない |
| `vehicleHasLoadHold` | 搬入判断待ち・積み置き中のため車両を無効化できない |
| `vehicleOnHold` | 搬入判断待ち・積み置き中で車両を使用できない |
| `vehicleHoldConflict` | 同じ車両に有効保留がある、または期待する保留状態ではない |
| `driverUnavailable` | ドライバーが存在しない、または無効 |
| `vehicleScheduleConflict` | 車両の時間が重複 |
| `driverScheduleConflict` | ドライバーの時間が重複 |
| `dispatchVersionConflict` | 配車版が更新済み |
| `invalidDispatchTransition` | 許可されない配車状態遷移 |
| `invalidOutcome` | 作業結果または必須メモが不正 |

既存の`success`、`duplicateSuccess`、`validationError`、`versionConflict`、`staleGeneration`、`idempotencyConflict`、`notFound`、`storageFull`、`storageUnavailable`も継続使用する。

画面は`success`または`duplicateSuccess`だけで完了表示へ進む。

## 19. 複数タブ同期

通知種別へ次を追加する。

```text
dispatch
dispatchStatus
internalNote
vehicle
driver
```

通知には変更種別、対象ID、発生日時だけを含め、予約内容、住所、電話番号、メモ本文を含めない。通知受信後はIndexedDBから最新データを読み直す。

- 他タブ更新で未保存入力を自動破棄しない。
- 保存時に予約版・配車版・世代を再確認する。
- 初期化・削除終了ではVer2の追加データとタブ内のドライバー選択を破棄する。
- タブが再び選択されたときにも最新スナップショットを読み直す。

## 20. 初期データ

### 20.1 移行直後

既存Ver1データを移行する場合は、車両とドライバーだけを追加し、配車と社内補足は空で開始する。既存の確定済み配車対象予約は未配車として確認できる。

### 20.2 Ver2完全初期データ

新規開始または明示的な初期状態への復元では、14番基本設計書の例を満たす架空データを用意する。

- 配車対象外の予約
- 確定済み・未配車
- 配車済み
- 回収中
- 全量回収済み
- 一部回収・要再配車
- 回収不可・要対応
- 全量回収済みの予約に紐づく、保留中の架空車両
- 配車後変更・要再確認
- 時間重複を確認できる予定
- 電話確認、量の不確実性、現場条件の社内補足

全データで参照先を存在させ、予約と配車の状態を矛盾させない。具体的な架空車両名、ドライバー名、件数、日付配置はテスト仕様・実装指示の作成前に確定する。

## 21. 初期化・削除・7日経過

- 初期状態へ戻す場合、Ver1の6ストアとVer2の4ストアを同じトランザクションで初期化する。
- 削除終了では、メタデータ以外の全9業務ストアを消去する。
- `DemoMetadata`だけを`deleted`で残し、新しい`generationId`を発行する。
- 最終利用から7日超の次回起動では、古い全10ストアのデータを使用せず、Ver2完全初期データを新世代として生成する。
- 初期化・削除と通常保存が同時成立しないよう、全ストアを対象とするreadwriteトランザクションで直列化する。
- 保存容量不足や破損の疑いだけを理由に自動初期化しない。

## 22. 個人情報と表示安全

- 公開デモの初期データはすべて架空情報とする。
- 社内補足と作業結果は顧客画面から取得できない。
- ドライバー画面は社内補足を取得・表示しない。
- 操作通知、コンソールログ、エラー監視へ住所、電話番号、自由記述本文を出さない。
- 監査履歴へ自由記述を重複保存しない。
- 文字列はHTMLとして実行しない。
- 初期版は同じブラウザ内のデモであり、本番の権限分離を保証しないことを明記する。

## 23. 初期版の対象外

- 本番認証と権限別データアクセス
- 複数端末・複数利用者間の共有DB
- サーバー側ロック、監査保管、バックアップ
- GPS、経路、通知、写真、署名、添付ファイル
- 積込回数、途中回収量、同日継続の保存
- 品目別の数値実績と単位変換
- 車両積載量・廃棄物種類・混載の自動適合判定
- 終了済み作業結果の編集・訂正機能
- 車両の削除、一括取込、車検・整備・保険・燃料・走行距離管理
- 勤怠管理との自動同期、ドライバーの一括取込
- マニフェスト、料金、請求、売上連携

## 24. データ・保存受入条件

| ID | 条件 |
|---|---|
| V2-DAT-01 | Ver1のDBをVer2へ更新しても既存予約、設定、停止、履歴、冪等記録が保持される |
| V2-DAT-02 | 新しい4ストアと必要な索引がDB版2で作成される |
| V2-DAT-03 | 移行可能な版不一致だけを理由に既存データを初期化しない |
| V2-DAT-04 | 配車対象外、未配車、配車済み、回収中、要再配車、要対応、要再確認を予約と配車から判定できる |
| V2-DAT-05 | 同じ予約に有効な配車を2件保存できない |
| V2-DAT-06 | 同じ車両またはドライバーの重複時間帯を保存できず、隣接時間は保存できる |
| V2-DAT-07 | 同日・同じ車両・同じ主担当ドライバーで継続する場合、配車・履歴・冪等記録が増えない |
| V2-DAT-08 | 一部回収では予約を確定のまま保持し、終了配車を残して次の配車を登録できる |
| V2-DAT-09 | 回収不可では予約を確定のまま保持し、要対応として判定できる |
| V2-DAT-10 | 全量回収では配車完了、予約完了、双方の履歴、冪等記録が一括保存される |
| V2-DAT-11 | 配車後の重要な予約変更で有効配車が要再確認となり、確認時の版とスナップショットを更新できる |
| V2-DAT-12 | 配車担当者の代理登録とドライバー登録を操作者で区別できる |
| V2-DAT-13 | 同じ処理の再送で配車、結果、社内補足、履歴が重複しない |
| V2-DAT-14 | 古い予約版、配車版、データ世代からの保存を拒否できる |
| V2-DAT-15 | 配車済み予約の取消では予約と配車が同時に取り消され、回収中予約の通常取消は拒否される |
| V2-DAT-16 | 初期化・削除終了・7日失効がVer2の追加4ストアを含めて成立する |
| V2-DAT-17 | 社内補足を追記専用で保存し、顧客画面・ドライバー画面・通知本文へ流出させない |
| V2-DAT-18 | 保存失敗・DB更新失敗時に既存データを自動初期化しない |
| V2-DAT-19 | 車両保留の開始・積み置き決定・解除を車両版と履歴付きで保存し、保留中の新規配車と回収開始を拒否できる |
| V2-DAT-20 | 回収結果と同時の保留開始が一括保存され、再送・保存失敗・初期化でも予約、配車、車両保留の整合が保たれる |
| V2-DAT-21 | 配車期限警告を保存せず、未配車の予約日と日本時間の今日から当日・前日・2日前へ正しく分類できる |
| V2-DAT-22 | ドライバーを一意コードで登録・版管理し、変更を監査履歴へ保存できる |
| V2-DAT-23 | 無効なドライバーを新規配車へ使用できず、未完了配車を持つドライバーの無効化を拒否できる |
| V2-DAT-24 | 車両コードを自動採番し、重複しない車両ナンバーで車両を登録・編集できる |
| V2-DAT-25 | 未完了配車または車両保留がある車両の無効化を拒否し、解消後は無効化・再有効化できる |
