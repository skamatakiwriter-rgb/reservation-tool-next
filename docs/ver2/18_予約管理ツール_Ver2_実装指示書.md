### 7.1 Repositoryの扱い

現在の`ReservationRepository`は初期化、世代、予約、履歴、冪等性をまとめている。Ver2初期版ではクラス名を一括変更せず、次の方針で拡張する。

- 配車用の公開メソッドを同じrepositoryへ追加する。
- 状態判定と入力検証は純粋関数へ分離する。
- 予約と配車を同時更新する処理は、同じIndexedDBトランザクション内で行う。
- 配車だけ別repositoryへ分けて、全量回収や予約取消を別トランザクションにしない。
- repositoryが過度に大きくなった場合は、トランザクションを受け取る内部ヘルパーへ分割し、公開保存契約は一つに保つ。

## 8. 実装する保存API

名称は実装に合わせて調整できるが、次の責任を持つ操作を用意する。

| 操作 | 主な入力 | 成功時の主な更新 |
|---|---|---|
| `createDispatch` | 世代、処理ID、操作者、予約ID、期待予約版、予定、車両、担当者、指示 | 配車、履歴、冪等記録 |
| `updateDispatch` | 配車ID、期待予約版、期待配車版、変更内容 | 配車、履歴、冪等記録 |
| `startDispatch` | 配車ID、期待予約版、期待配車版、操作者 | 回収中、開始履歴、冪等記録 |
| `completeDispatch` | 配車ID、期待予約版、期待配車版、結果、メモ、操作者 | 配車完了、必要なら予約完了、履歴、冪等記録 |
| `cancelDispatch` | 配車ID、期待予約版、期待配車版、理由、操作者 | 配車取消、履歴、冪等記録 |
| `acknowledgeDispatchReview` | 配車ID、配車版、予約版、操作者 | 最終確認版、スナップショット、履歴 |
| `addInternalNote` | 予約ID、本文、操作者 | 補足、履歴、冪等記録 |
| `startVehicleLoadHold` | 車両ID、回収済み配車ID、期待車両版、理由、相談状況、操作者 | 車両の搬入判断待ち、履歴、冪等記録 |
| `confirmVehicleLoadHold` | 車両ID、期待車両版、電話相談の判断内容、操作者 | 積み置き中、履歴、冪等記録 |
| `releaseVehicleLoadHold` | 車両ID、期待車両版、積載解消の理由、操作者 | 保留解除、履歴、冪等記録 |

既存の`updateReservation`と`changeStatus`は、有効配車の確認と一括更新に対応させる。配車対象の予約を`changeStatus(completed)`で直接完了させず、全量回収の`completeDispatch`を使用する。`completeDispatch`は実際に回収した場合に限り、搬入判断待ちの同時登録を受け付けて予約・配車・車両を一括保存する。Ver2では配車の有無にかかわらず既存予約のカテゴリー変更を`updateReservation`で拒否する。変更が必要なら予約取消後、既存の再受付機能で異なるカテゴリーの新予約を作成し、相互履歴を残す。数量などの申告内容の変更は、有効配車があれば要再確認にする。

同日継続用の`continueSameDay`、`addProgressReport`、`completeFirstLoad`等の保存APIは作らない。

## 9. 共通実装規則

### 9.1 保存順序

全保存操作で次の順を守る。

1. 現在の`generationId`を確認する。
2. 同じ世代の冪等記録を確認する。
3. 同じキー・同じ内容なら初回結果を返す。
4. 対象の存在、状態、版、入力、関連データを確認する。
5. 1つのreadwriteトランザクションで本体、履歴、冪等記録、メタデータを保存する。
6. トランザクション完了後だけ成功を返す。
7. 成功後に他タブへIDだけを通知する。

### 9.2 日時

- 予定日は`YYYY-MM-DD`、予定時刻は`HH:mm`で保存する。
- 開始・終了・作成・更新はISO日時を使用する。
- 日本時間の暦日判定を既存の日付関数と共有する。
- 同じ操作内で複数回`now()`を呼んで履歴時刻をずらさず、保存開始時の日時を共有する。

### 9.3 版

- 予約変更は予約版、配車変更は配車版を照合する。
- 配車登録・開始・終了・取消・変更確認も、画面で確認した予約版と配車版の該当する両方を照合する。
- 予約と配車を同時更新する場合は両方の最新状態をトランザクション内で確認する。
- 表示中の古いスナップショットを自動上書きしない。

### 9.4 エラー

- 画面へ保存サービスの識別可能な結果を返す。
- エラーをすべて同じ文言へ変換しない。
- 容量不足、DB利用不能、版競合、世代不一致、重複予定を区別する。
- 失敗時に入力を消去せず、自動初期化しない。

### 9.5 個人情報

- 社内補足本文を監査履歴、通知、コンソールへ複製しない。
- BroadcastChannelへ住所、電話番号、指示、結果メモを載せない。
- HTML文字列を実行しない。
- ドライバー画面用データ組立て時に社内補足を除外する。

## 10. 実装工程

前工程が合格するまで、依存する後工程を完成扱いにしない。各工程で関連自動テストを先に追加または同時追加する。

### 工程0：開始点の固定

作業内容：

- `main`の状態、開始コミット、タグ、Node.js、依存関係を記録する。
- Ver1の全自動テスト、型検査、Lint、本番ビルドを実行する。
- `feature/v2-dispatch-management`を作成する。
- 実装開始記録に基準結果を残す。

完了条件：

- Ver1基準検査が合格している。
- `main`と`v1.0.0`に変更がない。

### 工程1：型・カテゴリー・純粋な配車規則

作業内容：

- カテゴリーへ`requiresDispatch`を追加する。
- `Vehicle`（搬入判断待ち・積み置き中の任意記録を含む）、`Driver`、`DispatchAssignment`、`InternalNote`、作業結果、配車状態、操作者型を追加する。
- 配車表示状態、許可遷移、時間重複、車両保留による利用制限、結果別必須項目、配車期限の当日・前日・2日前判定を純粋関数として実装する。
- 同日継続は状態遷移や保存操作を持たないことをテストする。

主なテスト：

- `V2-SEED-04`～`08`
- `V2-DSP-T09`～`13`
- `V2-DSP-T19`～`22`
- `V2-OUT-04`～`08`

完了条件：型検査と純粋関数の単体テストが合格し、Ver1テストも合格する。

### 工程2：IndexedDB版2と移行

最優先の高リスク工程とする。UIより先に完成させる。

作業内容：

- DB版・スキーマ版を2へ上げる。
- 4ストアと16番文書の索引を追加する。車両保留は`vehicles`の任意項目と履歴に保持し、追加ストアは作らない。
- `onupgradeneeded`で既存ストアを削除しない。
- Ver1 activeデータを保持する論理移行を実装する。
- 版不一致を全初期化条件から分離する。
- DB接続へ`versionchange`時のclose処理を追加し、別タブ更新の阻害を減らす。
- 移行失敗を自動初期化へ変換しない。

主なテスト：`V2-MIG-01`～`10`。

完了条件：

- DB版1の既存レコードが内容・ID・版を保ってDB版2へ移行する。
- 移行再実行でマスター・履歴が重複しない。
- 失敗時に既存データを消去しない。

### 工程3：初期データとスナップショット

作業内容：

- 固定した車両・ドライバーを追加する。
- `DEMO-001`～`009`を維持し、`010`～`017`を追加する。
- 配車・結果・社内補足・要再確認・積み置きの整合した初期例を作る。
- `DemoSnapshot`へ4データを追加する。
- 初期化、削除終了、7日失効処理を10ストアへ拡張する。

主なテスト：`V2-SEED-01`～`09`、`V2-LIFE-01`～`08`。

完了条件：完全初期データの全参照が有効で、Ver1の既存9予約の意味が維持される。

### 工程4：配車登録・変更・取消の保存

作業内容：

- `createDispatch`、`updateDispatch`、`cancelDispatch`を実装する。
- `assigned`の通常変更は出発前として扱い、未着手確認の追加入力を設けない。車両・担当者変更は同じ配車IDとattemptを維持する。取消の確認ダイアログでは作業前の操作であることを示す。
- 有効配車1件、attempt連番、初回日付、再配車日付、車両・担当者重複を保存時に再確認する。
- 搬入判断待ち・積み置き中の車両への新規配車と変更を拒否する。保留開始前の既存配車は自動取消しない。
- 配車済み予約の取消を予約・配車一括処理へ拡張する。
- 保存結果と競合IDを画面へ返せるようにする。

主なテスト：`V2-DSP-T01`～`16`、`V2-RED-02`、`03`、`07`、`V2-EXC-T07`～`10`。

完了条件：二重配車と重複時間をトランザクション内で防止し、部分保存がない。

### 工程5：回収開始・作業結果・再配車

作業内容：

- `startDispatch`と`completeDispatch`を実装する。
- `startDispatch`は任意操作とし、`completeDispatch`は`assigned`と`inProgress`の両方を受け付ける。
- `assigned`から完了する場合は開始日時・開始操作者を生成しない。
- 全量回収では予約と配車を一括完了する。
- 搬入判断待ちを同時申告した場合は車両保留も一括保存する。電話相談後の積み置き決定と積載解消時の解除を保存し、保留中の車両は新規配車・回収開始を拒否する。
- 一部回収・回収不可では予約を確定のまま保持する。
- 操作者を`demo-admin`と`demo-driver:<id>`で区別する。
- 同日継続ではrepositoryを呼ばない。
- 終了済み配車を上書きせず再配車を追加する。

主なテスト：`V2-WRK-T03`～`09`、`V2-OUT-01`～`16`、`V2-RED-01`～`08`、`V2-HOLD-T01`～`08`。

完了条件：三つの作業結果と同日継続が16番文書どおり保存される。

### 工程6：社内補足・要再確認

作業内容：

- `addInternalNote`を追記専用で実装する。
- 予約変更時に重要項目を比較し、有効配車を要再確認にする。
- 既存予約のカテゴリー変更の拒否、取消後の新カテゴリー再受付、申告数量変更時の要再確認、予約日変更時の配車予定日の整合、既存の直接完了操作を保存処理で制御する。
- 割当時と最終確認時の予約スナップショットを保持する。
- `acknowledgeDispatchReview`を実装する。
- `assigned`かつ`needsReview=true`の配車開始・作業結果登録を拒否する。

主なテスト：`V2-NOTE-01`～`07`、`V2-EXC-T01`～`06`。

完了条件：補足が顧客・ドライバーへ流出せず、予約差分の確認基準が更新される。

### 工程7：複数タブ通知とデータhook

作業内容：

- 通知種別へ配車、配車状態、補足、車両、ドライバーを追加する。
- 通知には種別、ID、時刻だけを載せる。
- `useDemoData`で拡張スナップショットを読み込む。
- フォーカス・表示復帰時の再読込を維持する。
- 他タブ更新で編集中入力を自動破棄しない。

主なテスト：`V2-SYNC-01`～`12`。

完了条件：複数タブの更新反映と競合拒否が成立し、通知に個人情報がない。

### 工程8：ルート・入口・予約管理の拡張

作業内容：

- `/driver`を追加し、`/admin`を予約・配車管理として拡張する。
- デモ入口を利用者用、予約・配車管理、ドライバーの3入口へ整理し、共通の使い方ガイドへの導線を追加する。
- 共通ナビゲーションを追加する。
- `/admin`一覧へ予約状態とは別の配車状況と絞り込みを追加する。
- 日付の絞り込み対象を予約日と配車予定日から選べるようにする。
- 既存の管理画面の集計領域に配車状況別・本日予定・予定日超過の件数と一覧への導線を追加する。
- 搬入判断待ち・積み置き中の車両件数と、影響する将来配車への導線を別枠で表示する。
- 蛍光管は配車対象外と表示する。

主なテスト：`V2-UI-01`～`08`、`V2-REG-07`。

完了条件：`/`、`/reserve`、`/admin`、`/driver`の4URLを直接開いて再読込でき、Ver1の3URLが従来どおり動く。

### 工程9：予約一覧・予約詳細への配車統合

作業内容：

- 既存の`AdminPage`を拡張し、予約状態と配車状況を別表示する。
- 配車状況の絞り込み、検索、空状態、予約選択を実装する。
- 既存の予約詳細へ、依頼申告、社内補足、配車入力、作業結果、配車履歴を領域別に追加する。
- 配車対象予約では従来の直接完了ボタンを表示せず、配車対象外では維持する。
- 配車登録、変更、取消、要再確認、代理結果登録を接続する。
- 回収済み予約の詳細に、配車担当者用として搬入判断待ちの登録、電話相談後の積み置き決定、積載解消時の解除を追加する。解除予定日時は必須にしない。保留操作のデモ操作者は`demo-admin`とする。
- 保留中の車両を選択不可とし、既存の将来配車では自動取消せず警告する。
- 重複予定と版競合時に入力を保持し、重複する予約詳細への導線を表示する。

主なテスト：`V2-DSP-T01`～`16`、`V2-NOTE-01`～`07`、`V2-A11Y-01`、`02`。

完了条件：予約一覧から選んだ予約詳細で依頼確認と配車登録ができ、失敗時に成功表示しない。

### 工程10：ドライバー画面

作業内容：

- 架空ドライバー選択、今日・明日・今後7日・最大31日の任意期間、日付別担当一覧、案件詳細を実装する。

## 11. 工程ごとの検査コマンド

各工程で関連テストを実行し、工程の節目では必ず全体を実行する。

```text
npm test
npm run typecheck
npm run lint
npm run build
```

- テスト件数の増加だけで合格としない。
- 一部テストだけの成功で工程完了としない。
- Lint修正のために業務仕様を変えない。
- ビルド成果物へ実在情報、秘密値、外部API URLが含まれないことを別途確認する。

次のように、動作とテストが同時に確認できる単位でコミットする。

## 13. 禁止事項

- `main`、`v1.0.0`、既存公開サイトをVer2開発中に上書きしない。
- `git reset --hard`等で既存変更を消さない。
- スキーマ版・初期データ版の不一致だけでactiveデータを全初期化しない。
- DB版更新時に既存6ストアを削除・再作成しない。
- 配車状態を予約状態へ追加しない。
- 同日継続、電話報告、積込回数を必須保存にしない。
- 一部回収を作業途中の進捗として保存しない。
- 終了済み配車を上書きして再配車を表現しない。
- 回収中配車を取り消す管理者向け例外操作をVer2初期版へ追加しない。
- 画面上の重複警告だけを排他制御として使用しない。
- BroadcastChannelを正本またはロックとして使用しない。
- 社内補足を顧客画面・ドライバー画面・通知へ載せない。
- 申告量だけで車両を自動決定・保存拒否しない。
- 本番認証、GPS、経路、通知、写真、マニフェスト、売上連携を追加しない。
- 実在する勤務先、顧客、担当者、住所、電話、車両番号を使用しない。
- テストを削除・skipして検査を通さない。

## 14. 失敗時の復帰方針

### 14.1 実装中

- 失敗した工程のコミットを特定し、関連テストで再現する。
- 未関係のVer1コードを一括書換えしない。
- DB移行失敗時は自動初期化で隠さず、旧版データを保持した再現DBで原因を確認する。
- 仕様不足ならコードだけで仮決定せず、14～17番文書を補正する。

### 14.2 保存失敗

- トランザクション完了前に成功表示しない。
- 同じ処理IDで初回結果を照会する。
- 冪等記録がなければ未保存として入力保持・再試行を案内する。
- 容量不足やDB利用不能で自動初期化しない。

### 14.3 移行がblockedになる場合

- 他タブへ再読込・終了を案内する。
- 開いている接続は`versionchange`で閉じる。
- DB削除による回避を自動実行しない。

## 15. 実装完了条件

次をすべて満たした場合だけ、Ver2ローカル実装完了とする。

- `feature/v2-dispatch-management`上で実装され、`main`と`v1.0.0`が保護されている。
- Ver1回帰試験が合格している。
- 17番テスト仕様のP0が全件合格している。
- P1が全件合格、または影響と対応方針が記録されている。
- 全自動テスト、型検査、Lint、本番ビルドが合格している。
- DB版1から2への自動・実ブラウザ移行が合格している。
- 同日継続で不要なデータが増えない。
- 一部回収・回収不可・再配車・要再確認が履歴を保持して成立する。
- 搬入判断待ち・積み置き中の車両が新規配車・回収開始に使われず、解除後に再使用できる。
- 初期化、削除終了、7日失効が10ストアを対象に成立する。
- 社内補足と個人情報の表示境界を確認している。
- README、操作ガイド、CHANGELOG、受入記録が実装結果と一致している。
